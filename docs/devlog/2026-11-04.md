## 트러블슈팅: `'conda'은(는) 내부 또는 외부 명령...이 아닙니다`

VS Code 터미널(cmd)에서 `conda activate KS_Recoder`를 치자 이 에러가 났다. "갑자기" 안 되는 것처럼 보였지만, 사실은 **처음부터 안 되는 상태**였다.

- Anaconda 설치 기본값은 PATH에 등록하지 않는 것이다. 사용자 PATH와 시스템 PATH 어디에도 Anaconda 경로가 없었다.
- `conda init` 흔적(cmd의 `AutoRun` 레지스트리, PowerShell 프로필)도 없었다.
- 그래서 `conda`는 **Anaconda Prompt에서만** 동작했다. 지금까지는 전체 경로로 Python을 불러서 드러나지 않았던 것이다.

해결은 한 줄이다.

```
<Anaconda 설치 폴더>\condabin\conda.bat init cmd.exe powershell
```

터미널을 새로 열면 cmd에서는 바로 된다. PowerShell은 한 단계가 더 필요하다. Windows PowerShell 기본 실행 정책(Restricted)이 conda가 만든 프로필 스크립트를 막기 때문에, 현재 사용자 범위로 정책을 풀어 줘야 한다.

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

`RemoteSigned`는 내 PC에서 만든 스크립트는 실행하고, 인터넷에서 받은 서명 없는 스크립트는 계속 막는다.

## 싱크 분석 도구

카메라와 마이크를 따로 받아 합치는 구조라서, 두 장치의 **고정 지연 차이**가 얼마인지 실측해야 한다. 그래서 박수를 쳐서 재기로 했다.

1. 오디오를 5ms 블록으로 나눠, "배경 소음의 20배 또는 최대값의 20%"를 넘는 지점을 박수 후보로 잡는다.
2. 그 직전 10ms 안에서 소리가 처음 서는 샘플을 박수 시각으로 쓴다.
3. 박수 시각 앞 10프레임, 뒤 6프레임을 9:16 영역으로 잘라 한 장의 시트로 저장한다. 각 칸에 `dt`(프레임 시각 − 소리 시각)를 적는다.
4. 시트에서 손이 닿은 프레임의 `dt`가 곧 오프셋이다.

도구를 믿으려면 도구부터 검증해야 한다. **정답을 아는 합성 영상**을 만들었다. 1.500초에 화면이 하얗게 번쩍하고, 클릭 소리는 1.540초에 나는 영상이다.

| 정답 | 도구가 잰 값 | 오차 |
|---|---|---|
| 소리가 40ms 늦음 | 흰 프레임 `dt = -42ms` | 2ms |

2ms는 클릭 소리가 서서히 커지는 모양(Hanning 창) 때문에 생긴 차이라서, 실제 박수처럼 소리가 확 서는 경우엔 더 작아진다. 프레임 하나가 33ms이니 측정 도구로 충분히 쓸 만하다.

## 실측: 박수 녹화 4개

| 녹화 | 내용 | 목적 |
|---|---|---|
| ① ② | 15초, 박수 3번 | 오프셋이 매번 같은지 |
| ③ | 앱을 껐다 켠 뒤 15초, 박수 3번 | 카메라를 다시 열어도 같은지 |
| ④ | 12분 42초, 처음과 끝에 박수 3번씩 | 길게 찍으면 벌어지는지 (드리프트) |

4개 모두 **1920×1080, 모든 프레임 간격이 정확히 33.33ms**였다. 12분짜리도 22,877프레임 전부 같은 간격이다.

손이 부딪히는 순간을 찾으려고, 박수 소리 시각 기준으로 프레임마다 "앞 프레임과의 차이(움직임)"를 계산했다. 손이 빠르게 붙는 프레임에서 움직임이 정점을 찍는다.

| 녹화 | 소리 대비 움직임 정점 |
|---|---|
| ① | +26 / +32 / +30 ms |
| ③ | +30 / +9 / +37 / +41 ms |
| ④ 시작 | +42 / +37 / +18 ms |
| ④ 마지막 | +13 ms |

**소리가 화면보다 약 0~40ms 먼저** 나오고, 녹화를 다시 해도, 앱을 껐다 켜도, 12분이 지나도 같은 범위다.
사람이 어긋남을 알아채기 시작하는 기준(소리가 45ms 넘게 먼저)보다 작다. 그래서 **슬레이트 보정 기능은 만들지 않기로 했다.** 기능을 미리 만들었다면 쓸모없는 코드가 하나 늘었을 것이다.

## 트러블슈팅: 12분 녹화 끝에서 260ms가 어긋났다

④의 끝 박수 세 개 중 두 개가 이상했다. **손이 닿는 장면이 소리보다 약 260ms 먼저** 나왔다. 그런데 바로 다음 박수는 다시 정상(+13ms)이었다.

처음엔 시계 드리프트를 의심했다. 그래서 카메라 시계(`startTime`)와 마이크 시계(받은 샘플 수)를 PC 시계와 3분 동안 직접 비교했다.

| 시계 | PC 시계 대비 |
|---|---|
| 카메라 `startTime` | +16 ppm |
| 마이크 샘플 수 | +33 ppm |

12분이면 15ms 남짓이다. 드리프트가 아니었다. 오디오 길이(762.5714초)와 영상 길이(762.5667초)도 5ms 안에서 같았다.

다음으로 "앞 프레임과 거의 같은 프레임(=엔진이 복제한 칸)"이 어디 몰려 있는지 셌다.

```
복제 칸이 몰린 초: 0~1초, 19~22초, 758~760초
```

어긋난 두 박수가 정확히 758~760초 구간에 있었다. 이 구간에서는 프레임이 한 칸 걸러 하나씩 복제돼 있었다. **손이 렌즈 가까이 와서 화면이 어두워지자, 카메라가 노출을 늘리면서 fps를 15 정도로 낮춘 것**이다.

원인은 내 칸 배치 로직이었다. 흔들림에 휘둘리지 않으려고 "최근 0.5초 동안 계속 늦을 때만 복제"하게 만들었는데, fps가 갑자기 절반이 되면 프레임마다 칸을 2개씩 써야 한다. 그런데 0.5초가 쌓일 때까지 1칸씩만 채우니 **영상이 소리보다 점점 앞당겨졌다.**

먼저 이 상황을 재현하는 테스트를 썼다. 3초 정상, 2초 15fps, 2초 정상인 시각을 만들어 넣고, 어떤 프레임도 제 시각에서 한 칸(33ms) 넘게 벗어나지 않는지 검사한다.

```
E       assert 14.46875 < 1.0     ← 고치기 전: 최대 14.5칸(약 480ms) 어긋남
```

고친 규칙은 단순하다. 이제 프레임 시각은 Qt의 `startTime`에서 오기 때문에 흔들림이 0.47칸(타이머 틱 하나) 미만이다. 그러니 **한 칸 이상 늦은 프레임은 흔들림일 수 없고, 바로 그만큼 복제하면 된다.**

```python
lateness = (arrival - self.origin) * self._fps - self.next_slot
if lateness <= -1:                          # 같은 칸에 또 온 프레임
    ...
extra = max(extra, math.floor(lateness))    # 한 칸 이상 늦음 = 빠진 프레임 → 바로 채움
self._residuals.append(lateness - extra)    # 놓인 칸 기준 오차로 저장
```

한 가지 함정이 더 있었다. 처음엔 복제한 뒤 과거 지각값을 전부 한 칸씩 옮겼는데, 그러면 과거 프레임들이 "이르다"로 보여서 버림이 연달아 났다.
그래서 **각 프레임이 실제로 놓인 칸 기준의 오차(잔차)를 저장**하고, 속도 차이를 보정했을 때만 기록을 비우게 바꿨다. 테스트 17개가 모두 통과했고, 실제 카메라의 40초 `startTime` 데이터도 그대로 "복제 2 · 버림 0"이 나왔다.
