## 트러블슈팅: `python -m ks_studio` 했는데 아무것도 안 뜬다

터미널에는 이 두 줄만 찍히고 창이 보이지 않았다.

```
qt.gui.icc: fromIccProfile: Failed to parse description
qt.multimedia.ffmpeg: Using Qt multimedia with FFmpeg version 9.0.1 LGPL version 2.1 or later
```

두 줄 다 에러가 아니다. 첫 줄은 모니터 색 프로필(ICC)의 설명 문자열을 Qt가 못 읽었다는 경고이고, 둘째 줄은 Qt 멀티미디어가 FFmpeg 백엔드로 시작했다는 안내다.

프로세스 목록을 보니 앱은 멀쩡히 떠 있었고, 창 제목도 "KS Studio"였다. 그래서 창 좌표를 직접 확인했다.

| 대상 | 가로 범위 |
|---|---|
| 앱 창 | **-1714 ~ -99** |
| 메인 모니터 | 0 ~ 3413 |
| 세로 모니터 | 3413 ~ 4853 |

**창이 아무 모니터도 없는 왼쪽 바깥에 떠 있었다.** 지금까지는 창 위치를 Windows에 맡겼는데, 듀얼 모니터 환경에서 이런 좌표를 받은 것이다.

해결은 시작할 때 주 모니터의 작업 영역 가운데에 직접 놓는 것이다. 모니터가 창보다 작으면 창 크기도 줄인다.

```python
available = app.primaryScreen().availableGeometry()
window.resize(window.size().boundedTo(available.size()))
window.setGeometry(QStyle.alignedRect(Qt.LayoutDirection.LeftToRight, Qt.AlignmentFlag.AlignCenter,
                                      window.size(), available))
```

다시 실행하니 창이 x = 893 ~ 2508, 메인 모니터 가운데에 떴다.

> 교훈: "실행이 안 된다"는 "프로세스가 죽었다"와 "창이 안 보인다"를 먼저 나눠 봐야 한다. 이번엔 후자였다.

## 검증: 카메라가 10fps로 떨어졌을 때

어제 고친 "fps가 떨어지면 영상이 앞당겨지던 버그"를 실제 카메라로 확인하려고, 렌즈를 손으로 반쯤 가리고 박수를 치는 20초 녹화를 했다.

먼저 작은 사고가 하나 있었다. 녹화를 멈추자마자 앱을 닫아서, 백그라운드에서 돌던 마무리(MKV → MP4)가 중간에 끊겼다. 원본 MKV는 `.partial/`에 그대로 있었기 때문에 복구 함수로 바로 MP4를 만들 수 있었다. **복구 장치가 제 몫을 한 셈**이다.

결과는 예상보다 극단적이었다. 렌즈를 가린 구간만이 아니라 **녹화 전체가 약 10fps**였다. 아침 실내 조명만으로는 이 웹캠이 30fps를 못 낸다는 뜻이다.

엔진이 프레임을 제 시각에 놓았는지는 "복제가 아닌 진짜 프레임들 사이의 간격"으로 확인할 수 있다. 10fps라면 진짜 프레임은 3칸(100ms)마다 하나씩 있어야 한다.

| 진짜 프레임 사이 간격 | 횟수 |
|---|---|
| 3칸 | **156** |
| 2칸 / 4칸 | 23 / 24 (흔들림 ±1칸이 쌍으로 상쇄) |
| 1칸 | 1 |

고치기 전 로직이었다면 0.5초 동안 프레임이 1칸 간격으로 붙어서, 영상이 소리보다 앞서 나갔을 것이다. 이제는 **모든 프레임이 제 시각에서 한 칸(33ms) 안에** 놓인다.

다만 이번 녹화로 싱크 자체는 잴 수 없었다. 손이 렌즈를 덮고 있어서 박수 장면이 화면에 보이지 않았다. 측정 방법을 잘못 설계한 것이다. 렌즈를 가리는 대신 **방을 어둡게 해서** 다시 재기로 했다.

## 기능: 닫을 때 마무리가 끝날 때까지 기다리기

위의 "녹화 직후 앱을 닫아서 마무리가 끊긴" 사고는 복구로 살릴 수는 있지만, 사용자 입장에선 헷갈린다. 그래서 닫기 동작을 바꿨다.

- 녹화 중에 닫으면 → 녹화를 멈추고 마무리까지 한다.
- 마무리할 녹화가 남아 있으면 → 닫기를 미루고 대기 창을 띄운다. **닫기 버튼도, 취소도, Esc도 없다.** 끝나면 저절로 닫히고 앱도 종료된다.
- 대기 창에는 **"NN초 남음"**을 표시한다.

남은 시간은 마무리 함수가 영상 1초 분량마다 알려 주는 진행률로 계산한다.

```
남은 시간 = 남은 미디어 초 ÷ 최근 5초 동안의 처리 속도(미디어 초 / 실제 초)
```

예상 시간을 고정값(예: "실시간의 20배 속도")으로 두지 않고 실제 처리 속도로 잰 이유는, 디스크 속도나 다른 작업 때문에 매번 달라지기 때문이다.

12분짜리(2.3GB) 녹화를 마무리하는 도중에 창을 닫아서 검증했다.

| 닫은 뒤 | 표시 | 실제 남은 시간 |
|---|---|---|
| 2초 | 남은 시간 계산 중… | — |
| 7초 | 37초 남음 | 37초 |
| 14초 | 30초 남음 | 30초 |
| 30초 | 13초 남음 | 14초 |

처음 몇 초만 지나면 1초 안쪽으로 맞았다. 녹화 도중에 닫는 경우도 녹화 정지 → 5초짜리 MP4 완성 → 앱 종료까지 정상으로 동작했다.

## 컷편집기 MVP

녹화기를 마무리하고 컷편집으로 넘어왔다. 범위는 컷편집과 싱크 맞추기까지다. 자막·이미지는 AI 보정 뒤의 "마무리" 단계에서 넣는다. AI가 얼굴을 찾을 때 자막이 방해되면 안 되기 때문이다.

### 결과물은 영상이 아니라 `project.json`

컷편집의 결과물은 렌더링한 영상이 아니라 "어떤 원본의 몇 번 프레임부터 몇 번까지를 어떤 순서로"라는 결정 목록이다.

```python
@dataclass(frozen=True)
class Clip:
    source: str            # 프로젝트 폴더 기준 상대 경로
    in_frame: int          # 원본에서 쓰는 구간 [in, out)
    out_frame: int
    audio_offset_ms: int   # +면 소리를 늦춤
```

- **시간은 초가 아니라 프레임 번호(정수)다.** 녹화기가 정확한 CFR로 저장하니 프레임 단위로 딱 떨어지고, 소수점 오차가 쌓이지 않는다.
- **메인 트랙은 CapCut처럼 자석식이다.** 클립 사이에 틈이 없어서 타임라인 = 클립 목록이다. 지우면 뒤가 당겨지고, 끌어서 옮기면 순서만 바뀐다.
- **모든 객체가 불변(frozen)이다.** 편집 함수는 새 Project를 돌려주기만 한다. 그래서 되돌리기는 상태 스냅샷을 쌓는 것으로 끝난다. 커맨드 패턴을 쓸 필요가 없었다.

### 렌더러 하나를 세 곳에서 쓴다

`TimelineRenderer`는 타임라인 프레임마다 `(프레임 번호, 영상 프레임, 그 프레임 동안의 오디오 1600샘플)`을 낸다. 영상과 오디오가 한 묶음으로 나오니까 받는 쪽은 둘을 따로 맞출 필요가 없다. 미리보기, 임시 내보내기, 나중의 AI 보정이 전부 이걸 쓴다.

실제 녹화본으로 검증했다.

| 항목 | 결과 |
|---|---|
| 타임라인 프레임 = 원본의 정확한 프레임 | 픽셀 단위로 일치 |
| +50ms 오디오 오프셋 | 샘플 단위로 일치 |
| 미리보기(960×540) 렌더 속도 | **448fps** (실시간의 15배) |
| 찾아가기 1회 | 약 104ms (키프레임이 1초마다라 최대 30프레임 디코딩) |

### 트러블슈팅: 미리보기 화면이 소리보다 200ms 늦을 뻔했다

미리보기는 오디오를 기준 시계로 삼는다. 지금 스피커에서 나는 소리의 위치를 구하고, 그 위치의 프레임을 화면에 낸다. 처음엔 이렇게 계산했다.

```
재생 위치 = processedUSecs() − (출력 버퍼에 남은 양)
```

그런데 `QAudioSink.processedUSecs()`가 정확히 무엇을 세는지 문서만으로는 확신이 없어서 직접 쟀다.

```
wall 1.51s  written 1.70s  processed 1.50s  buffered 0.20s  written-buffered 1.50s
```

`processedUSecs`는 이미 "쓴 양 − 버퍼에 남은 양"이었다. 내 공식은 **버퍼를 두 번 빼고 있었고**, 그대로 뒀다면 화면이 소리보다 버퍼 크기(200ms)만큼 늦게 나왔을 것이다. 고친 뒤 재생 속도는 30.04fps, 재생 버튼을 누르고 첫 화면까지 204ms다.

### 워크스페이스와 미디어 가져오기

왼쪽 워크스페이스에는 프로젝트의 녹화본이 자동으로 뜨고, 외부 영상은 "+ 가져오기"나 탐색기에서 끌어다 놓기로 추가한다. 가져오는 방식은 설정에서 고른다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 프로젝트 폴더로 복사 (기본) | 폴더만 옮기면 다 따라감 | 디스크를 더 씀 |
| 원본 경로만 참조 | 복사 시간·용량 없음 | 원본을 옮기면 끊김 (타임라인에 빨갛게 표시) |

복사는 큰 파일도 UI가 멈추지 않게 스레드에서 `.part`로 쓰고 다 쓰면 이름을 바꾼다. 경로는 프로젝트 안이면 상대 경로, 밖이면 절대 경로로 `project.json`에 적는다.

### 타임라인

QPainter로 직접 그린다. 위에서부터 눈금자, 영상 줄(키프레임 썸네일 필름스트립), 오디오 줄(10ms 단위 파형)이다. 오디오 오프셋을 주면 파형이 그만큼 밀려 보인다.

말소리는 진폭이 작아서 파형을 그대로 그리면 거의 평평했다. 원본의 최댓값으로 나누고 √로 작은 소리를 키웠다.

마우스 조작은 실제 마우스 이벤트(QTest)로 검증했다. 끝을 60px 끌어 자르기(150 → 135프레임), 몸통을 끌어 순서 바꾸기, 눈금자 클릭으로 재생 헤드 이동, 워크스페이스에서 끌어다 놓기(경계 위치 계산)가 모두 기대대로 동작했다.

| 단축키 | 동작 |
|---|---|
| Space | 재생 / 정지 |
| ← / → | 1프레임 이동 |
| Ctrl+B | 재생 헤드에서 분할 |
| Delete | 선택한 클립 삭제 (뒤가 당겨짐) |
| Ctrl+Z / Ctrl+Shift+Z | 되돌리기 / 다시 하기 |

### 60fps 장비 대비: 타임라인 fps와 원본 fps 분리

지금 웹캠은 30fps지만 나중 장비는 60fps일 수 있다. 처음 구현은 "30fps 영상만 넣을 수 있음"이었다. 이러면 장비를 바꾸는 순간 예전 녹화본과 새 녹화본을 한 프로젝트에 섞을 수 없다.

상업용 편집기가 하는 방식대로 **타임라인(출력) fps와 원본 fps를 분리**했다.

- 타임라인 fps는 30 또는 60. 빈 타임라인에 처음 넣는 클립을 따라가고, 언제든 바꿀 수 있다.
- 클립은 원본 fps를 기억하고, in/out은 원본 프레임 번호로 저장한다.
- 렌더할 때 "타임라인 프레임 → 원본 프레임"으로 변환한다. 60→30은 하나씩 건너뛰고, 30→60은 같은 프레임을 두 번 쓴다 (가장 가까운 프레임 방식).
- 오디오는 프레임이 아니라 시간 기준이라 변환과 상관없이 맞는다.
- 원본 fps는 29.97처럼 **소수 그대로** 저장한다. 30으로 반올림하면 영상이 0.1% 빨리 흘러서 1분에 약 60ms씩 소리와 벌어진다.

```python
def source_frame(self, clip, local):   # 클립 안 타임라인 위치 → 원본 프레임
    return min(clip.out_frame - 1, clip.in_frame + math.floor(local * clip.fps / self.fps + 1e-9))
```

60fps 카메라가 없어서, 프레임마다 자기 번호를 2진 블록으로 새기고 원본 1.000초에 클릭 소리를 넣은 합성 영상으로 검증했다.

| 경우 | 원본 프레임 틀림 | 클릭 위치 |
|---|---|---|
| 60fps 원본 → 30fps 타임라인 | 0 / 90 | 1.0000s |
| 30fps 원본 → 60fps 타임라인 | 0 / 180 | 1.0000s |
| 29.97fps 원본 → 30fps 타임라인 | 0 / 90 | 1.0000s |
| 30 + 60 섞기 → 60fps 타임라인 | 0 / 120 | 0.5000s |

60fps 타임라인으로 내보낸 파일은 모든 프레임 간격이 16.67ms였고, 미리보기 재생도 60.07fps로 돌았다. 녹화 쪽은 60fps에서 한 칸(16.7ms)이 Windows 타이머 틱(15.6ms)과 거의 같아서, 틱 흔들림만으로 복제·버림이 생기지 않는지 테스트를 추가했다. 비트레이트는 fps에 비례해 올렸다 (60fps 녹화 50Mbps).

## 검토: 실제 휴대폰 영상과 휴대폰 웹캠 60fps

"VFR 외부 영상"과 "실제 60fps 카메라"를 남은 위험으로 적어 뒀는데, 갤럭시·아이폰으로 찍은 영상 3개와 휴대폰을 웹캠으로 연결해 우리 앱으로 찍은 60fps 녹화본으로 검토했다.

### 휴대폰 영상: VFR은 문제가 아니었다

| 파일 | 코덱 | 프레임 간격 | 회전 | 색 |
|---|---|---|---|---|
| 갤럭시 원본 | HEVC 10bit, 1920×1440 | 29.996fps, 390개 중 1개만 34ms | -90° | **HDR (HLG, BT.2020)** |
| 휴대폰 영상 A | HEVC 8bit, 1920×1080 | 정확히 30fps | -90° | SDR |
| 휴대폰 영상 B | HEVC 8bit, 1920×1080 | 정확히 30fps | 0° | SDR |

세 파일 모두 사실상 CFR이었다. A·B는 인코더 정보가 `Lavf58.45`라서 원본이 아니라 메신저 등을 거치며 다시 인코딩된 파일로 보인다.

대신 다른 문제 세 가지가 나왔다.

1. **한 프레임 늦은 장면.** 갤럭시는 30fps가 아니라 29.996fps다. "원본 프레임 = 내림(타임라인 위치 × 원본 fps / 타임라인 fps)"이라 비율이 1보다 아주 조금 작으면 항상 직전 프레임이 골라져서, 화면이 계속 **-32ms** 늦었다. 상업용 편집기의 기본값처럼 **가장 가까운 프레임**(딱 중간이면 앞 프레임)으로 바꾸자 평균 **+1.2ms**가 됐다.
2. **회전 무시.** 세로로 찍은 영상에는 "-90° 돌려서 보여라"는 정보가 붙어 있는데 이걸 무시하고 있었다. 실제로 렌더러로 뽑아 보니 옆으로 누운 채 16:9로 늘어나 있었다.
3. **HDR.** 갤럭시 원본은 HLG HDR이다. 그냥 8bit로 바꾸면 BT.2020 색을 BT.709로 읽어서 채도가 낮아진다.

### 휴대폰 웹캠 60fps: 카메라가 60장을 못 보낸다

녹화 파일 자체는 정확한 60fps CFR(826프레임, 전부 16.67ms)이었는데, 복제가 아닌 진짜 프레임은 650개뿐이었다. 카메라에서 직접 프레임 시각을 받아 재 봤다.

| 요청 포맷 | 실제로 받은 프레임 | 칸 배치 결과 |
|---|---|---|
| 1080p 60fps (NV12) | **47.5fps** (간격 16ms/32ms) | 복제 234 · 버림 0 |
| 1080p 60fps (JPEG) | 43.0fps | 복제 198 · 버림 0 |
| 1080p 30fps (NV12) | 26.7fps | 복제 39 · 버림 0 |

엔진은 빠진 칸을 복제로 정확히 채웠고 버림은 한 번도 없었다. 끊김의 원인은 카메라(휴대폰 웹캠) 쪽이다.

싱크는 달랐다. 박수 장면에서 손이 처음 닿는 프레임이 소리보다 **+109ms, +114ms** 늦었다. JOYTRON(0~40ms)보다 영상 지연이 훨씬 크다. 휴대폰이 영상을 압축해서 USB로 보내는 과정이 더해지기 때문으로 보인다. 사람이 알아채기 시작하는 기준(소리가 45ms 넘게 먼저)을 넘는다. 어제 "필요 없다"고 결론 냈던 **카메라별 싱크 보정이 이 장비에서는 필요하다.** 측정을 먼저 하고 기능을 정한 덕분에, 언제 필요한지가 숫자로 분명해졌다.

## 기능: 카메라·마이크별 박수 싱크 보정

휴대폰 웹캠에서 소리가 화면보다 약 100ms 먼저 나온다는 게 확인돼서, 박수로 재는 보정 기능을 앱에 넣었다.

- **보정 단위는 카메라 + 마이크 조합이다.** 지연은 영상 경로와 소리 경로의 차이라서 마이크만 바뀌어도 달라질 수 있다. 장치는 ID로 먼저 찾고 없으면 이름으로 찾는다. 같은 휴대폰이 "SAMSUNG_Android"에서 "USB 비디오 장치"로 이름이 바뀌어 떠도 ID로 찾아진다.
- **보정 전인 조합이면** 상단 장치 표시와 녹화 화면에 노란색으로 "싱크 보정 필요"가 뜬다.
- **"박수로 싱크 보정"** 버튼 → 안내 → 3·2·1 → 12초 녹화(보정 없이) → 소리에서 박수를 자동으로 찾는다 → 박수마다 앞뒤 프레임을 줄지어 보여 주고, 움직임이 가장 큰 프레임을 미리 골라 둔다 → 사람이 확인·수정 → 박수별 (손이 닿은 시각 − 소리 시각)의 **중앙값**을 저장한다.
- 손이 닿은 시각은 "처음 닿아 보이는 프레임"과 "그 직전의 다른 장면" 사이의 가운데로 잡는다.
- 보정값은 녹화 MKV 안에 태그(`KS_AUDIO_DELAY_MS`)로 같이 기록하고, **마무리할 때 오디오를 그만큼 늦추거나(앞에 무음) 앞당긴다(앞을 버림).** 앱이 죽은 뒤 복구할 때도 같은 값이 적용된다.

자동 추정은 박수 하나씩 보면 1~2프레임 빗나가기도 했다 (휴대폰 박수 2: 자동 +72ms, 실제 +100ms). 그래서 사람이 고칠 수 있게 했고, 중앙값을 써서 하나쯤 빗나가도 결과가 흔들리지 않게 했다. 기존 녹화본으로 돌려 보면 JOYTRON **+14ms**, 휴대폰 웹캠 **+100ms**가 나와서 앞서 손으로 분석한 값과 맞았다.

## 트러블슈팅: 메인 스레드가 멈추면 소리가 사라진다

보정 기능을 E2E로 돌리다가, 보정 직후 찍은 녹화의 **오디오가 통째로 비어 있는** 걸 발견했다. 원인을 좁히려고 마이크를 켜 둔 채 메인 스레드를 일부러 멈춰 봤다.

| 메인 스레드 멈춤 | 결과 (고치기 전) |
|---|---|
| 0.5초 | 정상 |
| 2.5초 | **소리 2.15초 분량이 사라짐** |

Qt의 마이크 입력 버퍼가 약 0.45초뿐이라, 그보다 오래 읽지 못하면 넘친 만큼 버려진다. 우리 엔진은 받은 샘플 수로 시간을 세기 때문에, 소리를 잃으면 **그 뒤 소리가 잃은 만큼 앞으로 당겨져 싱크가 깨진다.** 보정 기능에서 박수 분석이 메인 스레드를 몇 초 막은 게 방아쇠였지만, 사실은 녹화 엔진에 처음부터 숨어 있던 위험이었다.

세 겹으로 고쳤다.

1. **입력 버퍼를 5초로 늘렸다.** 2.5초 멈춤에서도 이제 하나도 잃지 않는다.
2. **그래도 잃으면 감지해서 샘플 번호를 건너뛴다.** "(도착 시각 − 받은 길이)"가 평소 기준점보다 0.2초 넘게 늦으면 잃은 것으로 보고 번호를 그만큼 건너뛴다. 녹화 엔진은 번호가 비면 무음으로 채우므로 이후 싱크가 유지된다. 7초 멈춤(버퍼 초과)에서 2.01초를 잃었지만, 오디오 위치 12.21초 = 실제 경과 12.20초로 시간이 맞았다.
3. **박수 분석은 백그라운드 스레드로 옮겼다.**

| 메인 스레드 멈춤 | 결과 (고친 뒤) |
|---|---|
| 2.5초 | 잃은 소리 없음 |
| 7초 | 2.01초를 잃었지만 감지 → 무음으로 채움 → 이후 싱크 유지 |

고친 뒤 E2E에서는 보정(+100ms) 저장 → 다음 녹화의 오디오 앞에 100ms 무음이 들어간 것까지 확인했다.

## 기능: 영상 줄 3개 — 위 줄이 아래 줄을 덮는다

컷편집 타임라인에 영상 줄이 하나뿐이라, 분할한 조각을 나눠 놓고 보기가 불편했다. 그래서 프리미어의 V1/V2/V3처럼 줄을 셋으로 늘렸다. 한 번에 다 하지 않고 네 단계로 나눴고, 오늘은 그 첫 단계다.

| 줄 | 동작 |
|---|---|
| V1 (메인) | 지금처럼 자석식. 빈틈 없이 붙는다 |
| V2, V3 | 원하는 시간에 놓는다. 빈틈 허용 |
| 겹친 구간 | 위 줄이 화면을 덮는다 (V3 > V2 > V1). 아무것도 없으면 검은 화면 |

**데이터.** V1은 원래대로 "순서만 가진 클립 목록"으로 두고, 위 줄은 `(클립, 줄, 시작 프레임)`으로 따로 담았다. 예전 프로젝트 파일은 위 줄이 빈 채로 그대로 열린다.

**화면 정하기.** 핵심은 `visible_segments()` 함수 하나다. 타임라인을 "이 구간엔 이 클립의 이 부분이 보인다"는 겹치지 않는 구간들로 펼친다. 렌더러·미리보기·내보내기가 전부 이 결과만 보고 그리므로, 덮기 규칙은 한 곳에만 있다. 덮였다가 다시 드러나는 V1 클립은 덮이기 전 위치를 기억하고 있어서, 그 시각의 장면을 정확히 이어서 보여 준다.

**편집 규칙.**
- 같은 줄에서 다른 클립과 겹치는 자리에는 **놓지 않는다.** 끄는 동안 빨갛게 표시된다. 대신 재생 헤드와 클립 끝에 달라붙게 해서 딱 붙여 놓기는 쉽다.
- Ctrl+B는 선택한 클립이 재생 헤드에 걸려 있으면 그것만 나누고, 선택이 없으면 걸린 줄을 전부 나눈다.
- 위 줄 클립은 앞쪽을 자르면 끝 위치가, 뒤쪽을 자르면 시작 위치가 고정된다.
- V1 조각을 위 줄로 올리면 V1의 빈자리는 자석식으로 바로 닫힌다 (캡컷과 같은 동작).

**검증.** 원본마다 다른 색을 칠하고 프레임 번호를 밝기로 새긴 합성 영상(V1 30fps, V2 60fps, V3 30fps)을 만들어 렌더 결과를 **프레임마다** 확인했다. 덮는 순서, 60fps 원본이 30fps 타임라인에서 한 장씩 건너뛰는 것, 위 줄이 끝나면 V1이 그 시각 장면으로 돌아오는 것까지 모두 맞았다. 실제 앱에서도 마우스로 분할 → 위 줄로 끌어 올리기 → V3에 놓기 → 겹치게 놓기(거부) → 되돌리기 → 내보내기 순서로 확인했다.

아직 위 줄 클립의 소리는 나지 않는다. 다음 단계에서 모든 줄의 소리를 섞고, 줄마다 음소거·숨김 버튼을 붙인다.

## 기능: 모든 줄의 소리 섞기 + 줄마다 👁·🔊 버튼

영상 줄 4단계 중 2단계. 이제 그 시각에 걸린 **모든 줄의 클립 소리가 섞여서** 나온다. 화면에서 위 줄에 덮인 V1 클립도 소리는 계속 난다.

줄마다 버튼 두 개를 붙였다. 프리미어처럼 **둘은 서로 영향을 주지 않는다.**

| 버튼 | 끄면 |
|---|---|
| 👁 화면 | 그 줄이 없는 것처럼 아래 줄이 보인다. 소리는 그대로 |
| 🔊 소리 | 그 줄의 소리만 빠진다. 화면은 그대로 |

- 끈 상태도 프로젝트에 저장되고, Ctrl+Z로 되돌릴 수 있다.
- 재생 중에 눌러도 멈추지 않고 그 자리에서 이어서 재생한다. 소리를 껐다 켰다 하면서 비교하기 좋다.
- 위 줄 클립은 아래쪽 얇은 띠에 파형을 그린다 (캡컷 오버레이 방식). 소리를 끈 줄의 파형은 회색, 화면을 숨긴 줄의 썸네일은 어둡게 그린다.
- 여러 소리를 더하면 1.0을 넘을 수 있어서, 넘는 부분만 잘라 찢어지는 소리를 막았다. 클립별 볼륨 조절은 나중에 붙인다.

**검증.** 원본마다 다른 높이의 음을 넣었다 (V1 440Hz, V2 1000Hz). 그리고 렌더한 소리를 주파수로 나눠 봤다.
- 둘 다 켜면 두 음이 다 들린다.
- V2를 끄면 1000Hz만 사라지고, V1을 끄면 440Hz만 사라진다.
- V2 오디오 오프셋 +100ms를 주면 소리가 정확히 1.1초에서 시작한다 (오차 2ms 안).
- V2 화면을 숨기면 화면은 V1이 되고, 1000Hz는 그대로 들린다.

실제 앱에서도 버튼을 클릭해서 내보낸 파일의 소리 크기를 쟀다. 모든 줄을 켰을 때는 위 줄 구간에 소리가 있었고, V2·V3를 끄자 그 구간이 무음이 됐다.

## 기능: 영상 줄 추가·삭제, 줄이 많으면 세로 스크롤

영상 줄 4단계 중 3단계. 줄 개수가 3개로 고정이던 것을 늘리고 줄일 수 있게 했다.

- **[+ 줄]** (줄 이름 칸 맨 위): 맨 위에 줄을 하나 추가한다.
- **줄 이름 칸 우클릭**: "이 줄 위에 줄 추가" / "이 줄 삭제".
  - 중간에 끼워 넣으면 위쪽 줄들이 클립·👁·🔊 상태와 함께 번호가 하나씩 밀린다. 그래서 화면과 소리는 그대로다.
  - 클립이 있는 줄을 지우면 **"클립 N개도 같이 지워집니다"** 확인 창이 뜬다. 빈 줄은 바로 지운다. 둘 다 Ctrl+Z로 되돌릴 수 있다.
  - V1(메인)은 지울 수 없고, 최소 2줄은 남는다. 새 프로젝트는 3줄로 시작한다.
- **세로 스크롤**: 줄이 화면보다 많으면 줄 영역만 움직이고, 눈금자와 줄 이름 칸은 제자리에 있다. 오른쪽 스크롤바나 Shift+휠로 움직이고, 클립을 끌다가 위아래 끝에 가면 자동으로 스크롤된다.

작은 결정 하나: 스크롤 위치를 "위에서 내린 양"이 아니라 **"아래에서 올린 양"**으로 저장했다. 위에서 재면 맨 위에 줄을 추가할 때마다 V1이 한 칸씩 아래로 밀려 화면 밖으로 나간다. 아래에서 재면 줄을 아무리 추가해도 V1과 A1은 제자리에 있다.

**검증.** 줄 끼워 넣기·삭제 전후로 타임라인 모든 프레임에 보이는 원본과 프레임 번호를 비교해서 바뀌지 않음을 확인했다. V5에 놓은 클립이 맨 위에서 덮고 소리도 섞이는지는 렌더 테스트로 확인했다. 실제 앱에서는 다음 순서로 확인했다.
1. [+ 줄]로 6줄 만들기 (V1 위치 그대로)
2. Shift+휠로 올려서 V6에 놓기
3. V3 위에 끼워 넣기
4. 클립이 있는 V2 삭제 → 확인 창
5. 빈 줄 삭제 → 확인 창 없음
6. 되돌리기, 내보내기 (1286프레임 = 타임라인 길이)

## 기능: 연동 — V1을 편집하면 위 줄 클립이 따라온다

영상 줄 4단계 중 마지막. V1은 자석식이라 클립을 지우면 뒤 클립이 당겨지는데, 위 줄 클립은 제자리에 남아 "이 장면 위에 얹은 자막·화면"이 엉뚱한 장면 위로 가곤 했다. 캡컷의 연동처럼, 위 줄 클립이 **시작 지점 아래에 있던 V1 장면에 붙어서** 같이 움직이게 했다.

| V1 편집 | 위 줄 클립 |
|---|---|
| 클립 삭제 | 그 클립 위에 붙은 것은 같이 삭제, 뒤쪽 것은 같이 당겨짐 |
| 순서 바꾸기 / 끼워 넣기 | 붙어 있던 클립과 같이 이동 |
| 앞쪽 자르기 | 원본의 같은 장면 위에 머묾 (그 장면이 잘려 나갔으면 클립 맨 앞) |
| 분할 | 그대로 |
| V1 끝 뒤 | V1 끝을 따라감 |

- **"붙은 장면"은 따로 저장하지 않는다.** 편집할 때마다 편집 전후의 V1을 클립 id로 비교해서 다시 계산한다. 그래서 위 줄 클립을 옮기면 자연스럽게 새 장면에 붙는다. 분할하면 뒤 조각은 새 id가 되므로, 같은 원본을 쓰는 새 조각도 찾아본다.
- 따라가다 같은 줄의 다른 클립과 겹치면 바로 위 빈 줄로 올리고, 빈 줄이 없으면 맨 위에 줄을 만든다. 편집 자체를 거부하면 "삭제가 안 되는" 이상한 상황이 생기기 때문이다.
- 모든 편집이 지나는 한 곳(`_apply`)에서 적용한다. 그래서 V1 편집과 위 줄 이동이 **Ctrl+Z 한 번**으로 같이 돌아간다.
- 기본으로 켜져 있고, 편집 화면의 **🔗 연동** 버튼으로 끌 수 있다 (프로젝트마다 저장).

**검증.** 경우마다 "위 줄 클립 시작 지점 아래 V1의 원본 프레임"이 편집 전후로 같은지 확인했다. 실제 앱에서도 다음을 확인했다.
- 가운데 조각 삭제 → 그 위 V3 삭제, V2는 150프레임 당겨짐
- Ctrl+Z 한 번으로 전부 복구
- 마우스로 마지막 조각을 맨 앞으로 끌기 → 위 줄이 같이 이동
- 연동을 끄고 삭제 → 위 줄 제자리

## 버그 수정: 타임라인 fps를 바꾸면 위 줄 클립 위치가 어긋남

1단계에서 남긴 버그다. 위 줄 클립의 시작 위치는 타임라인 프레임 번호로 저장되는데, 30 → 60fps로 바꿀 때 이 번호를 그대로 둬서 **시각이 절반으로 당겨졌다.** fps를 바꿀 때 같은 시각이 되도록 번호를 함께 바꾸게 고쳤다.

## 기능: 컷편집 도구모음과 빠른 컷 편집 (M1)

단축키만으로는 기능을 찾기 어렵다는 피드백이 있었다. 그래서 타임라인 바로 위에 **도구모음**을 만들었다. 버튼과 단축키는 같은 동작 객체(`QAction`) 하나에서 만들어서, 둘이 어긋날 일이 없다. 버튼 툴팁에는 단축키가 같이 적혀 있다.

```
↶ 되돌리기 ↷ 다시 하기 | ✂ 분할 ⇤ 앞 자르기 뒤 자르기 ⇥ 🗑 삭제 ⧉ 복제 | [ 구간 시작  구간 끝 ] 구간 지우기 구간 해제 | ⏮ 이전 컷 다음 컷 ⏭ ····· 🧲 스냅 🔗 연동 | － ＋ ⤢ 맞춤
```

| 기능 | 단축키 | 동작 |
|---|---|---|
| 앞/뒤 자르기 | Q / W | 재생 헤드 앞(뒤)을 잘라낸다. 선택한 클립이 없으면 V1. V1은 빈자리가 닫힌다 |
| 구간 지우기 | I / O → Shift+Del | 모든 줄에서 구간을 잘라내고 뒤를 당긴다. 구간은 눈금자에 청록색 띠로 보인다 |
| 이전/다음 컷 | ↑ / ↓ | 모든 줄의 클립 시작·끝으로 재생 헤드를 옮긴다 |
| 스냅 | S | 끄고 켤 수 있다. 클립 끝을 끌어 자를 때도 재생 헤드·클립 끝에 달라붙는다 |
| 줌 | = / - / \ | 재생 헤드를 화면의 같은 자리에 둔 채 확대·축소·화면 맞춤 |
| 이동 | Shift+←/→, Home/End | 1초씩, 처음/끝으로 |

구간 지우기는 연동과 함께 쓸 때 조심할 점이 있었다. 구간 지우기가 이미 구간 뒤 위 줄 클립을 당겨 놓았는데, 연동이 한 번 더 당기면 두 번 움직인다. 연동은 "편집이 직접 옮긴 클립은 건드리지 않는다"는 규칙이 있어서 두 번 움직이지 않는다. 이걸 테스트로 못 박았다.

## 기능: 여러 클립 선택·복사·붙여넣기·복제 (M2)

- **선택:** Ctrl/Shift+클릭으로 더하거나 빼고, 빈 곳을 끌면 박스로 고른다. 빈 곳을 클릭만 하면 예전처럼 재생 헤드가 이동한다. Ctrl+A는 모두 선택.
- **삭제:** 선택한 클립을 한 번에 지운다 (V1은 빈자리가 닫히고, 연동이 적용된다).
- **복사/붙여넣기:** Ctrl+C / Ctrl+V. V1 클립은 재생 헤드의 편집점에 끼워 넣고, 위 줄 클립은 서로 간격을 유지한 채 놓는다. 자리가 차 있으면 위 빈 줄로 올린다. 붙여 넣은 클립은 바로 선택되어 있다.
- **복제:** Ctrl+D 또는 ⧉ 복제 버튼. 각 클립 바로 뒤에 놓는다.
- **우클릭 메뉴:** 클립이나 빈 곳을 우클릭하면 복사·붙여넣기·복제·분할·앞/뒤 자르기·삭제가 나온다. 도구모음과 같은 동작 객체를 그대로 써서, 쓸 수 없는 항목은 함께 비활성화된다.

여러 클립을 한꺼번에 끌어 옮기는 기능은 넣지 않았다. V1(자석식)과 위 줄을 섞어 옮기는 규칙이 복잡해서, 끌기는 클릭한 클립 하나만 옮긴다.

## 기능: 하단 상태 표시줄

여기저기 흩어져 있던 상태 글을 앱 맨 아래 한 줄로 모았다. 크게 띄울 정보는 아니지만, 늘 보여야 하는 정보다.

- **왼쪽, 알림:** 녹화 시작, 저장됨, 마무리 실패, 붙여넣기 N개, 구간 지우기 1.20초 같은 글. 일반 알림은 6초, 경고는 15초 뒤에 사라지고, 오류는 다음 알림이 올 때까지 남는다. 지나간 알림은 마우스를 올리면 최근 20개를 볼 수 있다.
- **오른쪽, 늘 보이는 표시:**
  - `● REC 00:12` (빨강)
  - 싱크 보정 상태: "⚠ 싱크 보정 필요"는 노랑, 보정했으면 "싱크 보정 +100ms". 상단 바에 있던 경고를 여기로 옮겼다.
  - fps: 녹화 화면에서는 **카메라가 실제로 보내는 fps**를 1초마다 잰다. 설정보다 10% 넘게 낮으면 노란 경고를 띄운다. 컷편집에서는 재생할 때 화면에 실제로 낸 fps를, 멈춰 있을 때는 타임라인 fps를 보여 준다.
- **로그:** 프로그램 안의 경고·오류 로그("원본을 읽을 수 없음", "마이크 샘플 손실" 등)도 여기로 모았다. 로그는 녹화·렌더 스레드에서도 남기 때문에, 핸들러가 Qt 시그널로 메인 스레드에 넘긴다.

실제 장비로 돌려 보니 바로 쓸모가 있었다. 방이 어두워서 JOYTRON이 **10fps**로 떨어져 있었는데, 상태 표시줄에 `카메라 10.0fps ⚠ 설정 30fps보다 낮음 (조명 확인)`이 떴다. 예전에는 녹화본을 열어 봐야 알 수 있던 문제다.

카메라 fps를 셀 때 한 가지를 신경 썼다. 프레임마다 메인 스레드로 이벤트를 보내지 않고, 카메라 스레드에서 정수 하나만 올린다. 녹화 엔진이 이미 같은 스레드에서 프레임 시각을 찍고 있어서, 가볍게 끼어들어야 했다.

## 기능: 휴대폰 영상용 편집용 사본 (리졸브 방식)

휴대폰으로 찍은 원본은 그대로 편집하기가 곤란했다. 실제 샘플을 보니 문제가 여러 겹이었다.

| 원본 | 문제 |
|---|---|
| 갤럭시 | 세로 회전 정보, HDR(HLG) BT.2020, 10bit |
| 아이폰 | 세로 회전 정보, Display P3 색역, 풀 레인지, **위치(GPS) 메타데이터** |
| 다시 저장된 영상 | 세로 회전 정보 |

우리 렌더러는 회전 정보를 무시하고 색 변환도 하지 않았다. 그래서 세로 영상이 옆으로 누워 늘어나 보이고, HDR은 색이 바랬다. DaVinci Resolve의 "최적화 미디어"처럼, **가져올 때 편집하기 좋은 사본을 따로 만드는** 방식으로 풀었다.

- **사본 형식:** H.264 8bit, BT.709 SDR, 회전을 픽셀에 적용, 30/60fps 고정(CFR), AAC 48kHz. 메타데이터는 옮기지 않아서 GPS도 따라오지 않는다.
- **사본 위치:** 프로젝트 `cache/optimized/`. 지워도 다시 만들 수 있다. `project.json`에는 원본 경로가 그대로 남는다.
- **읽기:** 미리보기·썸네일·파형·내보내기 모두 사본을 읽는다. `SourceCache.media()` 한 곳에서 "사본이 있으면 사본"을 정해서, 나머지 코드는 사본의 존재를 모른다. 캐시도 사본 기준이라 사본이 생기면 저절로 새로 만든다.
- **워크스페이스 표시:** "편집용 사본 만드는 중 74% (세로 회전·P3 색역→BT.709·풀 레인지)" → "편집용 사본 ✓". 사본이 준비되기 전에는 타임라인에 넣을 수 없다. 넣는 순간의 원본 정보(fps 등)가 사본과 달라 어긋나는 일을 막기 위해서다.
- **필요 없는 파일은 그대로:** 일반 가로 영상이나 우리 녹화본은 "사본 필요 없음"으로 판정되어 사본을 만들지 않는다.

**zscale 없이 HDR 다루기.** PyAV에 들어 있는 FFmpeg에는 흔히 쓰는 zscale이 없다. 대신 HLG가 "SDR 화면에서도 대충 맞게 보이도록" 설계된 곡선이라는 점을 이용했다. `colorspace` 필터에 BT.2020 SDR 감마로 넣고 BT.709로 바꾸면 자연스러운 색이 나온다. 실제 갤럭시 HLG 영상으로 확인했다. PQ(HDR10)는 이 근사로는 어둡게 나올 수 있어서 이유에 "근사"라고 표시한다. 아직 샘플이 없다.

**결과 (실제 원본):**

| 원본 | 걸린 시간 | 사본 | 오디오 어긋남 |
|---|---|---|---|
| 갤럭시 HLG 10bit 13초 | 4.8초 | 1440×1920 30fps | 0.00ms |
| 아이폰 P3 5초 | 1.3초 | 1440×1920 30fps | 0.00ms |
| 세로 회전만 7초 | 0.8초 | 1080×1920 30fps | 0.00ms |

**같이 바꾼 것:**
- **화면 비율이 다른 클립은 늘리지 않는다.** 세로 영상을 가로 캔버스에 넣으면 가운데에 놓고 양옆을 검게 둔다. 렌더러와 썸네일이 같은 함수를 쓴다. 예전 썸네일 캐시는 늘어난 그림이라 이름을 바꿔 새로 만들게 했다.
- **CPU 인코더로 대신하기.** 오픈소스로 공개할 프로그램이라 NVIDIA GPU가 없는 PC도 생각해야 했다. 인코더를 미리 열어 보고, NVENC가 안 되면 libx264(CPU)로 만든다. 테스트에서 NVENC가 64×48 같은 아주 작은 화면을 못 여는 것도 발견해서, 그 경우도 같은 길로 처리된다.

## 기능: 클립 볼륨·페이드, 무음 자르기 (M3)

**볼륨·페이드.** 속성 창에서 볼륨(dB), 페이드 인, 페이드 아웃(ms)을 정한다. 선택한 클립이 여러 개면 전부에 적용된다.
- 페이드는 프레임이 아니라 ms로 저장한다. 타임라인 fps를 바꿔도 길이가 그대로다.
- 클립을 나누면 페이드 인은 앞 조각에, 페이드 아웃은 뒤 조각에만 남는다. 나눈 자리에서 소리가 줄었다 커지는 일이 없다.
- 타임라인에는 소리 칸 위에 어두운 삼각형과 선으로 페이드를 그린다. 볼륨을 바꾸면 파형 크기도 따라 바뀐다.
- 실제 내보내기에서 -6dB 클립의 소리 크기가 원본의 **0.500배**였다 (이론값 0.501).

**무음 자르기 (🔇 버튼).** 말하는 영상에서 숨 고르기나 침묵을 한 번에 잘라낸다.
1. "이보다 조용하면 무음"(dB), "이만큼 이어지면 자르기"(ms), "앞뒤로 남길 여유"(ms)를 정한다. 기본값은 -40dB, 600ms, 150ms.
2. 값을 바꾸면 찾은 구간 목록이 바로 바뀐다. 보고 나서 "자르기"를 누른다.
3. 잘라내기는 구간 지우기를 **뒤에서부터** 반복한다. 앞에서부터 지우면 뒤 구간의 위치가 당겨져 엉뚱한 곳을 지운다. 되돌리기 한 번에 전부 돌아온다.

무음 판정은 V1 클립의 **들리는 소리** 기준이다. 오디오 오프셋으로 소리를 밀어 둔 클립이면 그만큼 옮겨서 계산한다. 박수만 친 녹화로 돌려 보니 박수 사이 무음 5곳, 11.9초를 정확히 찾아냈다.

## 기능: 화면 속 화면 · 디졸브 · 마커 (M4)

**화면 속 화면.** 클립마다 크기·위치·투명도가 생겼다.
- 속성 창에서 %로 바꾸거나, 미리보기에서 선택한 클립을 **끌어서 옮기고 Ctrl+휠로 크기**를 바꾼다. 선택한 클립에는 노란 점선 테두리가 그려진다.
- 끄는 동안에는 화면만 다시 그리고, 손을 뗄 때 편집 한 번으로 남긴다. 그래서 되돌리기도 한 번이면 된다.
- 렌더러는 "맨 위 클립 하나만 그리기"에서 **"화면을 다 덮는 맨 위 클립을 바탕으로, 그 위 클립들을 차례로 섞어 그리기"**로 바뀌었다. 기본값(크기 100%·가운데·불투명) 클립은 지금처럼 화면을 덮으니까, 대부분의 구간은 예전의 빠른 길을 그대로 탄다.
- 미리보기 비율을 결과물 캔버스(첫 클립 크기)에 맞췄다. 전에는 미리보기가 늘 16:9라서, 세로 캔버스라면 위치가 어긋났을 것이다.

**디졸브 (T, 캡컷 방식).** 뒤 클립이 앞 클립 끝과 겹치면서 서서히 나타나고, **겹친 만큼 전체 길이가 짧아진다.** 원본 앞뒤에 여분 프레임이 없어도 바로 쓸 수 있다.
- 겹친 동안 소리도 교차한다. 앞 클립은 작아지고 뒤 클립은 커진다.
- 길이는 속성 창 "앞 디졸브"에서 바꾼다. 클립을 다 먹거나 앞 디졸브와 겹치지 않게 자동으로 줄인다.
- 타임라인에는 겹친 곳을 노란 X자로 그린다. 클립을 나누면 디졸브는 앞 조각에만 남는다.

**마커 (M).** 재생 헤드에 놓고 지운다. 눈금자에 노란 표시로 보이고, ↑/↓ 편집점 이동이 마커에서도 멈춘다. 구간 지우기나 무음 자르기를 하면 뒤 마커도 같이 당겨지고, fps를 바꾸면 같은 시각으로 옮겨진다.

## 트러블슈팅: 화면 속 화면을 재생하면 25fps로 떨어진다

처음 재보니 화면 속 화면 구간 재생이 25/60fps였다. 그런데 렌더러만 따로 재면 137fps가 나왔다. 렌더러 문제가 아니었던 것이다. 원인은 세 겹이었다.

1. **측정 스크립트가 원인을 하나 더 얹고 있었다.** 테스트의 대기 함수가 이벤트를 처리하는 사이사이 20ms씩 잠들어서, 메인 스레드가 절반은 화면을 못 그렸다. 정상 이벤트 루프로 다시 재니 50~55fps였다.
2. **타임라인이 매 프레임 통째로 다시 그려졌다.** 재생 헤드가 움직일 때마다 파형 선 수천 개를 파이썬 루프로 그리면서 GIL을 오래 잡았다. 그 사이 렌더 스레드가 밀렸다. 그래서 재생 헤드를 뺀 타임라인 그림을 캐시해 두고, 재생 중에는 캐시를 베낀 뒤 빨간 선만 새로 그리게 했다.
3. **윈도우 기본 타이머는 15.6ms 단위다.** 60fps(16.7ms)에서는 가끔 두 프레임이 한 번에 몰리고, 그중 하나가 버려졌다. 재생 타이머를 정밀 타이머로 바꿨다. 미리보기 테두리 계산도 재생 중에는 건너뛰게 했다.

결과: 화면 속 화면 재생 **60/60fps**.

## 구조 변경: 다섯 단계, 서로 독립

"녹화 → 컷편집 → AI 보정 → 마무리"를 꼭 차례로 밟을 필요는 없다. 그래서 탭을 **촬영 / 컷편집 / AI 보정 / 자막 / 내보내기**로 나눴다. 탭마다 워크스페이스(프로젝트 미디어)에서 바로 가져와 작업하고, 결과물은 파일로 다시 워크스페이스에 쌓인다.

AI 보정을 자막보다 앞에 둔 이유가 있다. 자막이 먼저 얼굴 위에 박히면 얼굴 인식이 흔들리고, 글자까지 보정된다(콧볼 축소로 글자가 휜다). 그래서 자막은 영상에 굽지 않은 층으로 들고 있다가 내보낼 때만 합친다. 자막·내보내기 탭은 지금은 자리만 있다.

## 기능: AI 보정 기반 (InsightFace)

**패키지.** InsightFace 2.1 + onnxruntime-gpu. 처음 깔았을 때 GPU가 잡히지 않았는데, insightface가 CPU용 onnxruntime을 같이 깔면서 GPU판을 덮어썼기 때문이다. 둘 다 지우고 `onnxruntime-gpu[cuda,cudnn]`만 다시 깔았더니 RTX 5080에서 CUDA로 돈다. 1080p 한 프레임의 얼굴 찾기와 106점 랜드마크가 **약 12ms**다. 모델(약 600MB)은 처음 쓸 때 `models/`에 내려받고, 저장소에는 올리지 않는다. AI는 선택 설치(`[ai]`)라서 깔지 않아도 앱의 나머지는 그대로 돈다.

**흐름.** 사용자의 요청대로, 효과를 실제로 입히기 전에 확인하는 단계를 넣었다.
1. 영상을 고르면 영상 전체를 고르게 24곳 훑어서, 구간마다 **얼굴이 가장 잘 보이는 장면 4개**를 샘플 컷으로 고른다.
2. 샘플마다 보정 전·후를 나란히 보여 주고, 블러셔·콧볼 축소 슬라이더를 움직이면 바로 다시 그린다.
3. **[이 설정으로 OK]**를 누르면 아무 장면이나 스크럽하는 전·후 미리보기로 넘어간다. 얼굴 점 표시도 켤 수 있다. 느린 PC는 미리보기를 끌 수 있다.
4. **[보정본 만들기]**를 누르면 영상 전체 얼굴을 한 번 분석해서 캐시해 둔다. 강도를 바꿔 다시 만들 때는 분석을 건너뛴다. 그다음 `ai/<이름>_보정.mp4`를 만든다. 보정본은 컷편집 워크스페이스에 "AI 보정본"으로 나타난다.

**효과 (기본형).**
- **블러셔:** 눈 바깥 끝·콧볼·볼 윤곽 사이 "볼 사과" 자리에, 가장자리로 갈수록 옅어지는 타원으로 색을 섞는다. 얼굴 기울기를 따라 돈다.
- **콧볼 축소:** 양쪽 콧볼을 코 가운데로 당기는 국소 변형(Gustafsson). 반지름 끝은 변형이 0이라 경계가 티 나지 않는다.
- **떨림 줄이기:** 랜드마크가 프레임마다 조금씩 흔들려서, 영상 전체 분석 결과를 앞뒤 2프레임 평균으로 부드럽게 한다. 한두 프레임 얼굴을 놓쳐도 이웃 값으로 채워서 효과가 깜빡이지 않는다.

**실제 영상으로 잡은 문제 세 가지.**
1. **옆얼굴·뒤통수에 블러셔가 칠해졌다.** 코끝이 두 눈 가운데에서 얼마나 벗어났는지로 "정면 정도"를 재서, 옆으로 돌수록 효과를 서서히 줄인다. 화면에서 아주 작은 뒤쪽 얼굴도 줄인다. 0/1로 끊지 않아서 고개를 돌려도 깜빡이지 않는다.
2. **뒤통수를 얼굴로 착각했다.** 그 오탐의 점수가 0.53이었고, 진짜 얼굴은 0.66~0.86이었다. 점수 0.6 미만은 버린다.
3. **보정본이 깨졌다.** PyAV는 첫 패킷을 쓸 때 스트림 시간 단위를 1/30에서 1/15360으로 바꾼다. 그 뒤에도 프레임 시간 단위를 스트림에서 읽고 있어서 프레임 시각이 겹쳤다. 고정된 1/fps를 쓰게 고치고, 프레임 시각이 일정한지 테스트로 못 박았다.

**남은 문제.** 주인공이 화면에 없는 장면에서는 "가장 큰 얼굴"이 행인일 수 있고, 그러면 행인에게도 블러셔가 칠해진다. 샘플 컷 4장 중 1장이 그랬다. 다음 단계에서 주인공을 정해 그 사람만 보정하도록 할 계획이다.

## 기능: 보정할 사람(주인공) 고르기

"가장 큰 얼굴을 보정"하는 규칙은 주인공이 화면에 없는 장면에서 무너졌다. 행인이 가장 큰 얼굴이 되어 블러셔가 칠해졌다. 그래서 InsightFace 모델팩에 들어 있는 **얼굴 인식 모델**(얼굴마다 512차원 값을 내고, 같은 사람이면 비슷한 방향을 가리킨다)로 사람을 구분하게 했다.

- **사람 목록:** 샘플 후보 24장면의 얼굴을 같은 사람끼리 묶어서, 샘플 화면 위에 얼굴 썸네일로 보여 준다. 많이 나온 순이고, 처음에는 **가장 많이 나온 사람**이 선택되어 있다. 클릭하면 그 사람으로 바뀐다.
- **보정 대상:** 고른 사람과 닮은 얼굴만 보정한다. 샘플 컷·미리보기·보정본 모두 같다. 그 사람이 없는 장면은 아무것도 건드리지 않는다.
- **다시 확인:** 사람을 바꾸면 보정 대상이 달라지니까 OK가 풀리고 샘플부터 다시 확인한다. 영상 전체 분석 캐시도 사람마다 따로 둔다.

실제 값으로 경계를 정했다. 같은 사람 정면끼리 유사도는 0.48~0.5, 다른 사람과는 최대 0.18이었다. 그래서 0.35 이상을 같은 사람으로 본다. 고개를 완전히 돌려 귀만 보이는 장면은 같은 사람이어도 0.07까지 떨어졌다. 그래서 사람 목록은 **정면에 가까운 얼굴로만** 만든다. 그런 장면은 어차피 정면 가중치 때문에 보정이 들어가지 않는다.

**확인:** 테스트 영상에서 사람 7명을 찾았고, 주인공(6장면)이 기본으로 잡혔다. 샘플 4장이 모두 주인공이 됐다. 행인만 나오는 장면은 미리보기에서 "보정할 사람이 없는 장면"으로 나오고, 보정본에서도 원본 그대로였다(차이가 다시 인코딩할 때 생기는 수준).

**알려 둘 제약:** 유리에 비친 흐릿한 얼굴도 "사람"으로 목록에 나온다. 흐릿한 얼굴은 인식값이 불안정해서 다른 얼굴과 잘못 묶이기도 한다. 주인공은 선명하게 여러 번 나오니까 고르는 데는 지장이 없다.

## 트러블슈팅: AI 모델이 "bad allocation"으로 안 열린다

4K 영상을 AI 보정 탭에서 고르자 얼굴 모델을 여는 순간 `bad allocation`이 났다. 원인은 영상이 아니라 PC였다. 게임이 커밋 메모리를 14.5GB 잡고 있었고, **Windows 페이지 파일이 꺼져 있어서** 커밋 한도가 RAM 크기(32GB)와 같았다. 실제 RAM은 6.5GB 남아 있었는데도 "예약"할 수 있는 메모리가 0.2GB뿐이었다. 게임을 끄자 커밋이 16.7GB 남았고, 같은 4K 영상으로 샘플 컷·사람 목록·미리보기가 정상으로 돌았다.

재 보니 AI 모델을 열면 커밋이 약 2.5GB 는다. 대부분 CUDA·cuDNN 라이브러리 몫이다. 게임과 같이 쓰려면 페이지 파일을 켜 두는 게 안전하다.

## 개선: 편집용 사본 — 필요 없는 사본 안 만들기, 끝 프레임 버그

"사본 만들기가 느리다, GPU로 할 수 없나"를 확인하다가 더 큰 문제 두 가지를 찾았다.

1. **필요 없는 사본.** 20분짜리 4K 영상(HEVC 10bit, BT.709 SDR)이 "10bit"라는 이유 하나로 8분 넘게 13GB 사본을 만들고 있었다. 색이 이미 SDR BT.709면 렌더러가 그대로 읽을 수 있다. 그래서 10bit만으로는 사본을 만들지 않게 했다. 회전·HDR 같은 다른 이유로 사본을 만들 때만 10bit도 같이 8bit로 바꾼다.
2. **끝 0.4초가 사라졌다.** 사본을 만들 때 디코더가 마지막까지 들고 있던 프레임을 꺼내지 않고 버렸다. 13초 갤럭시 영상이 391프레임이어야 하는데 379프레임이었다. 끝을 알리는 빈 패킷도 디코딩해서 남은 프레임을 꺼내게 고쳤다. 예전 코드로는 실패하는 테스트로 못 박았다(60프레임 중 48프레임).

**GPU 디코딩은 해 봤지만 넣지 않았다.** 단계별로 재 보니 갤럭시 HEVC 디코딩은 GPU(NVDEC)가 3배 빨랐다(8.3 → 2.6ms). 하지만 회전·색 변환은 CPU에서 해야 한다. 이 FFmpeg에는 HDR 색 변환 GPU 필터가 없다. 그래서 GPU에서 푼 프레임을 내려받고 형식을 바꾸는 비용이 더 들었고, 전체는 오히려 느려졌다(5.0 → 8.7초). 그 과정에서 GPU 프레임의 레인지가 두 번 줄어 밝기가 뜨는 문제도 테스트로 잡았다.

**대신 한 것:**
- 디코딩을 따로 스레드로 돌린다.
- 필터 그래프에 스레드 4개를 준다. 기본은 1개였다. 색 변환 필터 단독으로는 프레임당 15.9 → 8.6ms다.
- 전체로는 8% 정도 빨라졌다. 파이썬 GIL 때문에 단계들이 완전히 겹치지는 못한다. 휴대폰 영상은 CPU 색 변환이 한계다.

| 영상 | 예전 | 지금 |
|---|---|---|
| 20분 4K 10bit SDR | 8분+, 13GB 사본 | **사본 없음** |
| 갤럭시 HLG 13초 | 5.3초 (끝 12프레임 잃음) | 5.1초 (전부) |
| 아이폰 P3 5초 | 1.9초 (끝 14프레임 잃음) | 2.1초 (전부) |

## AI 보정 다듬기: 경고·속도·3장 비교·얼굴 갸름

**insightface 경고.** insightface 2.1이 scikit-image에서 폐기 예정인 `SimilarityTransform.estimate`를 써서 경고가 났다. 2.2에서는 아예 없어진다. 라이브러리 파일을 고치면 다시 깔 때 되돌아가므로, 모델을 열 때 `face_align.estimate_norm`을 새 API(`from_estimate`)로 같은 계산을 하는 함수로 바꿔 끼웠다. 예전 함수와 결과가 같고, 경고를 오류로 바꾼 엄격한 모드에서도 얼굴 찾기·인식이 정상이다.

**샘플 고르기 속도.** 오래 걸리는 이유는 모델이 아니었다. 모델 열기는 1.6초다. 후보 장면마다 **정확한 프레임**을 풀려고 앞 키프레임부터 수십 장을 풀고 있었고, 4K에서는 장면당 2.7초였다. 샘플 후보는 정확한 프레임일 필요가 없어서, 가까운 키프레임만 푼다. 키프레임 간격이 너무 길어 후보가 뭉치는 영상만 그 후보를 정확한 프레임으로 푼다. 20분 4K 영상이 **약 67초 → 6.6초**가 됐다. 화면에는 진행바와 "약 N초 남음"을 띄운다.

**원본 · 적용 범위 · 적용 후.** 샘플 컷마다 세 장을 나란히 보여 준다. 적용 범위는 효과별 반투명 영역(턱선 노랑, 콧볼 하늘, 볼 분홍)과 움직임 화살표로 그린다. 처음엔 원을 하나하나 그려서 겹친 원이 덩어리가 됐다. 효과마다 영역을 한 번에 칠하고 한 번만 섞도록 바꿨다. 선 두께도 화면이 아니라 얼굴 크기를 기준으로 한다.

**얼굴 갸름.** 볼 아래~턱선 양쪽 7점씩을 얼굴 가운데 선(두 눈 가운데~턱 끝) 쪽으로 당긴다. 처음엔 점마다 차례로 변형했더니 이웃 변형끼리 겹쳐 **턱선이 물결쳤다.** 모든 점의 움직임을 하나의 매끄러운 변형장으로 합쳐 한 번에 적용하자 깨끗해졌다. 점 가까이에선 그 점의 움직임을 따르고, 멀어질수록 0이 된다. 콧볼 축소도 같은 방식으로 바꿨다.

**같이 잡은 버그.** 블러셔 위치를 계산할 때 오른쪽 볼 윤곽점이 한 칸 어긋나 있었다(27·28 → 28·29). 106점 배치에서 왼쪽 1,9~16과 오른쪽 17,25~32는 같은 순서로 짝을 이룬다. 처음 확인한 정면 사진에서 27·28이 맞아 보였던 건 고개가 기울어 있었기 때문이었다. 좌우 대칭 테스트가 이걸 잡아냈다.

## 트러블슈팅: 컷편집 미리보기가 BufferError로 안 나온다

세로 휴대폰 영상(1440×1920)을 타임라인에 올리자 미리보기가 `BufferError`를 내며 비었다. 미리보기 크기를 960×540 상자에 맞추면 폭이 404px가 된다. PyAV는 프레임을 numpy로 바꿀 때 줄마다 정렬용 여백을 붙이는데, 이 폭에서는 여백 때문에 배열이 메모리에 연속으로 놓이지 않는다. QImage는 연속 배열만 받는다. 화면에 넘기기 직전에 연속 배열로 바꿔(`np.ascontiguousarray`) 해결했다. 404px 프레임으로 테스트를 추가했고, 실제 앱에서 30/30fps로 재생되는 것도 확인했다.

## 개선: AI 보정본 화질 — 왜 떨어졌고 어떻게 지켰나

"원본에 바로 효과를 넣으면 화질이 유지되지 않나?"라는 질문에서 시작했다. 효과를 0으로 두고 다시 압축만 해서 원본과 비교해 보니(PSNR, 50dB 이상이면 눈으로 구분 불가) 보정본이 **42.7dB**였다. 원인은 세 가지였다.

1. **화면 전체를 RGB로 바꿨다 되돌렸다.** 효과는 RGB에서 넣는데 영상은 YUV다. 이 왕복만으로 47dB까지 떨어진다. → 얼굴 주변만 RGB로 바꾸고, **효과가 실제로 바꾼 화소만** YUV로 되돌려 쓴다. 배경과 효과가 닿지 않은 얼굴 둘레는 원래 값 그대로다(비트까지 같은지 테스트).
2. **인코더 품질 설정이 먹지 않았다.** NVENC는 품질 목표(cq)를 줘도 평균 비트레이트 기본값에 묶인다. `b=0`과 넉넉한 최대 비트레이트를 같이 줘야 cq대로 나온다. cq 16/14/12 = 48.2/49.8/51.4dB를 재서 12로 정했다.
3. **휴대폰 영상은 두 번 압축됐다.** 원본 → 편집용 사본(1번) → 보정본(2번). → 보정본을 만들 때 원본에서 회전·색 변환과 보정을 **한 번에** 하고 한 번만 압축한다.

| 경로 | 예전 | 지금 |
|---|---|---|
| 녹화본 → 보정본 | 42.7dB | **51.4dB** (85MB → 108MB) |
| 휴대폰(아이폰) → 보정본 | 41.1dB (압축 2번) | **46.4dB** (1번) |
| 휴대폰(갤럭시) → 보정본 | 38.0dB | **43.5dB** |

휴대폰 쪽 수치가 녹화본보다 낮은 건 손실 때문이 아니다. 비교 기준(무손실 변환)과 HDR→SDR 색 변환 단계가 같지 않아서 생기는 차이다. 파일은 원본보다 1.3~2배 커진다. 보정본은 편집 재료라서 화질을 우선했다. 최종 내보내기 화질(현재 16~20Mbps)은 내보내기 단계에서 따로 다룬다. 부수 효과로 렌더도 빨라졌다(15초 1080p 14.7 → 6.1초).

## AI 보정 효과 13가지

뷰티 앱 조사에서 "랜드마크만으로 가능"으로 분류한 효과를 모두 넣었다. 슬라이더는 탭 세 개로 나눴다.

| 탭 | 효과 | 방법 |
|---|---|---|
| 피부 | 매끈하게 · 톤 밝게 · 다크서클 | 피부 영역(윤곽+이마 아래쪽 − 눈·눈썹·입술)에 가장자리를 지키는 흐리기 / 밝기 올리기, 눈 밑 타원 밝게 |
| 얼굴형 | 얼굴 갸름 · 광대 축소 · 턱 길이(±) · 눈 키우기 · 콧볼 축소 · 코 길이 | 점 당기기 변형장, 눈은 가운데 확대(경계에서 기울기까지 1로 이어지는 식) |
| 메이크업 | 블러셔 · 립 컬러 · 치아 미백 · 눈 또렷하게 | 입술은 Lab에서 색(a·b)만 바꾸고 밝기는 그대로(결·윤기 유지), 치아는 입 안 밝은 화소의 노란기만, 눈은 언샤프 |

**순서가 중요했다.** 색(피부·메이크업)을 먼저 입히고 변형(얼굴형)은 마지막에 한다. 그래야 색 영역이 랜드마크와 딱 맞고, 변형이 칠해진 피부를 같이 옮긴다. 윤곽 변형 세 가지(갸름·광대·턱)는 서로 붙어 있어서 하나의 변형장으로 합쳤다. 따로 하면 이음매가 물결친다.

**속도.** 처음엔 13가지를 다 켜면 1080p 프레임당 89ms였다. 세 가지를 고쳤다.
- 큰 부드러운 영역(피부·눈 밑)은 얼굴을 줄인 크기에서 만들어 늘린다.
- 눈·눈 밑 작업은 그 영역만 계산한다.
- 변형은 점마다 자기 반지름 안만 계산한다.

그 결과 **34ms**가 됐다. 8가지를 켠 15초 영상의 보정본은 얼굴 분석 포함 19초에 나온다.

**적용 범위 그림**은 켠 효과만 효과별 색으로 칠한다. 13가지를 옅게라도 다 그리면 알아볼 수 없었다.

**한계.** 이마 위 머리카락선은 랜드마크로 알 수 없다. 앞머리가 이마를 덮으면 피부 영역에 머리카락이 조금 들어간다. 흐리기가 가장자리를 지켜서 티는 크지 않다. 잡티 제거·웃는 입·윤곽 메이크업·아이섀도는 이번에 넣지 않았다.
