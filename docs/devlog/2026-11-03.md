# [개발일지 #1] 웹캠 녹화기 만들기 — 빈 폴더에서 CFR 녹화 엔진까지

> 2026-11-03 · Python 3.12 · PySide6 6.12 · PyAV 19

## 무엇을 만드나

한국어 교육 콘텐츠(인스타 릴스)를 찍기 위한 **Windows용 녹화 + 컷편집 + AI 보정 + 내보내기** 데스크톱 앱이다.
흐름은 네 단계로 나눴다.

```
녹화  →  컷편집  →  AI 보정  →  마무리(자막·이미지 + 내보내기)
```

AI 보정은 얼굴 요소(볼, 콧볼 등)를 인식해서 블러셔를 넣거나 콧볼을 살짝 줄이는 식의 보정을 할 예정이다.
딥러닝 생태계를 쓰려고 **Python으로 끝까지 가기로** 했다. C++은 프로파일링으로 병목이 확인된 곳만 나중에 고려한다.

## 오늘 추가한 기능

- [x] 개발 환경 (conda 환경 `KS_Recoder`, Python 3.12)
- [x] 앱 뼈대: 상단 단계 바 + 4단계 화면 (CapCut 비슷한 패널 배치)
- [x] 설정 창: 카메라·마이크 선택, 실시간 미리보기, 마이크 레벨 미터, 작업 폴더 지정
- [x] 장치가 빠지면 경고 (기본 장치로 몰래 넘어가지 않음)
- [x] 녹화기: 3-2-1 카운트다운, 경과 시간, Space로 시작/정지, 9:16 세로 가이드
- [x] 녹화 엔진: 1080p **고정 프레임레이트(CFR)**, H.264(NVENC) + AAC
- [x] 5초 테스트 녹화 → 바로 재생해서 확인
- [x] 녹화 중 앱이 죽어도 다음 실행 때 복구

## 프로젝트 구조

유지보수를 생각해서 의존 방향을 한쪽으로만 흐르게 했다.

```
src/ks_studio/
├─ core/       순수 파이썬 (Qt import 금지) — 설정, 워크스페이스, CFR 칸 배치
├─ services/   바깥 세상과 닿는 곳 — 장치, 녹화 엔진, 마무리(MKV→MP4)
├─ ui/         화면 — 단계별 페이지, 공용 위젯
└─ app/        조립 지점 — 경로, 앱 실행
```

`ui → app → services → core` 방향으로만 import한다. 덕분에 `core`는 Qt 없이 pytest로 바로 테스트할 수 있다.
나중에 붙일 `ai/` 패키지도 Qt에 의존하지 않게 해서 별도 프로세스로 돌릴 수 있게 할 생각이다.

## 설정 창: "기본 장치로 몰래 넘어가지 않기"

막상 장치 목록을 찍어 보니 **Windows 기본 마이크가 웹캠 내장 마이크**로 잡혀 있었다.
기본 장치를 그대로 쓰면 좋은 마이크를 꽂아 두고도 웹캠 마이크로 녹음하는 사고가 난다. 그래서 이렇게 만들었다.

- 처음 실행하면 "장치 미설정"으로 경고하고, 사용자가 직접 골라야만 동작한다.
- 저장해 둔 장치가 없으면 콤보에 `⚠ 연결 안 됨 — 장치이름`을 띄우고 다른 장치로 바꾸지 않는다.
- 장치는 **ID로 먼저 찾고, 없으면 이름으로** 찾는다. 카메라 ID에 USB 포트 경로가 들어 있어서 포트만 바꿔 꽂아도 ID가 달라지기 때문이다.

그리고 웹캠(JOYTRON HD20)이 **1080p에서 최대 30fps**라는 것도 이때 알았다. 60fps는 이 카메라에선 불가능하다.

## 녹화 엔진 고르기: Qt 녹화기 vs 직접 파이프라인

처음엔 Qt의 `QMediaRecorder`로 쉽게 가려고 했다. 그런데 실험해 보니 문제가 줄줄이 나왔다.

| 항목 | A. Qt QMediaRecorder | B. PyAV 직접 파이프라인 |
|---|---|---|
| MKV + H.264 | ❌ **MPEG-4로 몰래 바뀜** | ✅ |
| A/V 시작 차이 | ❌ 영상이 1.0초 늦게 시작 | 직접 제어 |
| 프레임 간격 | ❌ 32/48ms로 흔들림 (VFR) | ✅ 33.33ms 고정 |
| 녹화 중 강제 종료 | ❌ **MP4 22MB 전체 손상** | ✅ 재생 가능 (마지막 약 1초 손실) |

결국 **B 방식**으로 갔다. 카메라 프레임과 마이크 샘플을 따로 받아서 하나의 파일로 직접 쓰는 방식이다.

```
QCamera ─▶ QVideoSink ─┬─▶ 미리보기 (좌우반전)
                       └─▶ NV12 프레임 복사 + 시각 ─┐
QAudioSource(마이크) ─▶ 샘플 묶음 + 번호 ─────────┼─▶ 쓰기 스레드 (PyAV)
                                                  │   H.264 NVENC + PCM → .partial/xxx.mkv
녹화 종료 ─▶ 마무리 스레드: 영상 복사 + PCM→AAC ──▶ xxx.mp4
```

- **MKV로 먼저 쓰는 이유:** MP4는 파일 끝에 목차(moov)를 써서, 녹화 중에 죽으면 통째로 못 연다. MKV는 쓰는 도중에도 읽을 수 있다.
- **PyAV에 NVENC가 들어 있다:** 1080p를 Python 안에서 **초당 269프레임**으로 인코딩했다. ffmpeg 실행 파일을 따로 동봉할 필요가 없어졌다.

## 트러블슈팅

### 1. ffmpeg 설치했더니 PySide6가 안 뜬다

conda-forge에서 ffmpeg를 설치하자마자 `import PySide6.QtCore`가
`DLL load failed: 지정된 프로시저를 찾을 수 없습니다`로 죽었다.

원인은 ffmpeg 의존성을 맞추는 과정에서 **Python 자체가 conda-forge 빌드로 교체**된 것이었다(`conda list --revisions`로 확인). 그러면서 DLL 검색 경로가 달라졌다.
`conda install --revision 0`으로 롤백하고, ffmpeg는 PyAV에 내장된 것을 쓰는 걸로 방향을 바꿨다.

> 교훈: Qt를 쓰는 conda 환경에 conda-forge 패키지를 섞을 땐 리비전 기록부터 확인하자.

### 2. 녹화했는데 오디오 트랙이 없다

```python
session.setAudioInput(QAudioInput(mic_device))  # ❌ 바로 GC로 사라짐
```

PySide에서 부모 없는 Qt 객체를 변수에 담지 않으면 Python이 바로 지워 버린다. 변수에 담아 두니 해결됐다.

### 3. 프레임이 31ms, 47ms 간격으로 들어온다

CFR을 맞추려면 "프레임이 언제 찍혔는지"를 알아야 한다. 측정해 보니 도착 간격이 이랬다.

```
arrival hist: [(31.0, 132), (32.0, 41), (47.0, 25), ...]
```

31ms와 47ms는 15.6ms의 2배, 3배다. **Windows 타이머 틱(15.625ms)에 맞춰 프레임이 전달되고 있었다.**
`timeBeginPeriod(1)`로 타이머 해상도를 올려 봤지만 그대로였다. 우리 프로세스가 아니라 카메라 드라이버 쪽에서 생기는 일이기 때문이다.

게다가 이 카메라의 실제 속도는 **29.946fps**였다. 30fps 칸과 아주 조금씩 벌어진다.

### 4. 복제/버림 10% → 2% → 0%

녹화 시작부터 1/30초 간격의 "칸"을 두고, 프레임을 도착 시각에 가장 가까운 칸에 넣는 방식(`FrameSlotter`)으로 시작했다. 결과는 이랬다.

| 시도 | 방법 | 300프레임 중 복제/버림 |
|---|---|---|
| 1 | 도착 시각을 반올림해서 칸에 배치 | 30 / 29 (10%) |
| 2 | 칸 기준점을 "가장 일찍 도착한 위상"에 맞춤 + 한 칸 미만 지각은 허용 | 12 / 10 (2%) |
| 3 | 최근 0.5초 중 **가장 덜 늦은 값**이 0.6칸을 넘을 때만 복제·버림 | 40초 실측 재생: **2 / 0** |

핵심 아이디어는 이거였다. **지연은 늦어질 수만 있으니, 최근 구간의 최솟값이 흔들림을 뺀 진짜 어긋남이다.**

```python
self._recent.append((arrival - self.origin) * self._fps - self.next_slot)
drift = min(self._recent)
if drift <= -LIMIT:          # 카메라가 빠름 → 하나 버림
    ...
return self._advance(math.floor(drift + 1 - LIMIT) if drift >= LIMIT else 0)
```

기준선을 0.5칸이 아닌 0.6칸으로 둔 것도 중요했다. 0.5칸으로 두면 복제한 직후 값이 정확히 -0.5가 돼서 바로 버림이 일어나는 진동이 생겼다.
40초 동안 29.946fps 카메라는 30fps보다 약 2.1프레임이 모자라니, "복제 2 · 버림 0"이 이론값 그대로다.

### 5. 콜백에서 찍은 시각이 16~31ms 흔들린다

UI에서 녹화할 때 다시 복제/버림이 튀었다. Python 콜백 안에서 `time.monotonic()`을 찍으면 GIL이나 NVENC 초기화 때문에 시각이 밀리는 거였다.

Qt가 프레임에 붙여 주는 `QVideoFrame.startTime()`을 60초 동안 비교해 보니, PC 시계와의 차이가 **1ms 안에서 거의 그대로**였다. 같은 시계라는 뜻이다.
그래서 칸 배치는 `startTime`으로 하고, 오디오와 맞출 때만 "PC 시계 − startTime"의 최솟값으로 환산하게 바꿨다.

### 6. MP4 프레임 간격이 33.31 / 33.38ms

MKV의 시간 단위가 1ms라서, MP4로 옮길 때 시간 단위가 1/16000으로 잡혔다. 그래서 33.33ms가 정확히 떨어지지 않았다.
마무리 단계에서 타임스탬프를 **프레임 번호로 다시 매기고**, 출력 스트림의 `time_base`를 1/30으로 지정하니 모든 프레임이 정확히 33.33ms가 됐다.
